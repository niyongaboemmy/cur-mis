01

Deliberation must record a decision per student

New table + endpoints Largest item Needs a decision
“Deliberation no kwimura abanyeshuri bava muri Level imwe, gusibiza ndatse no kumufatira umwanzuro, kwimura Promotion.”
What it asks for

The deliberation board must be able to move a student out of a level — promote them to the next one, make them repeat the level, or otherwise rule on their case — and have that promotion actually take effect on the record.

Where the code stands

Deliberation today is a marks review only. DeliberationController serves a grid, exports the board's XLSX, and finalizeSession() flips module_marks.status to confirmed for the whole programme. Nothing writes a per-student outcome, and nothing touches student.current_level. Promotion does not exist anywhere in the backend — the word appears in no controller, model or migration.

What to build
  • Migration 143: deliberation_decisions — one row per student per session, holding the outcome (promote, repeat_level, repeat_modules, discontinue, defer), the level moved from and to, a reason, the deciding user and timestamp.
  • POST /api/deliberation/sessions/:id/decisions to record or amend decisions in bulk from the grid, gated on MANAGE_DELIBERATIONS.
  • Extend finalizeSession() to apply the decisions: write the new student.current_level and, where the board discontinued a student, the matching student_state — reusing the status-change trail from item 03 so a level move and a state change leave the same audit record.
  • In DeliberationMarksView.tsx, an outcome column per student with a suggested default computed from the honours/pass rules, overridable by the board, plus a session summary showing how many promote / repeat / discontinue before finalising.
  • A printable deliberation minute — the report item 06 also asks for.
Decide before building

Is finalising a session irreversible? Today it locks marks and refuses re-entry. Once it also rewrites levels, an error is far more expensive — the board needs either an unlock path for a superadmin, or a mandatory preview-and-confirm step that shows every level change before it is written.

02

Marks uploaded from a system-issued template

Mostly done — harden it Small
“Upload y'amanota hakoreshejwe Templete bakuye muri system.”
What it asks for

Marks should be entered by downloading a template out of the system, filling it in offline, and uploading it back — not typed row by row.

Where the code stands

This already works. ModulesMarksPage.tsx exports the class roster as XLSX and imports CSV/XLS/XLSX back through SheetJS, with a preview modal before anything is applied. The gap is that the round-trip is entirely client-side: the file is matched on a “Reg #” column heading, and if a lecturer renames or reorders columns the import fails with a toast rather than a useful error. Nothing on the server ever sees the file.

What to build
  • GET /api/marks/template?module_id=&academic_term_id= — the server issues the workbook, with a hidden sheet carrying the module and term id so an upload can prove which sheet it came from. Identity columns are locked; only the mark columns are writable.
  • Server-side validation on import: unknown registration numbers, marks out of range, a locked or confirmed sheet, and a template issued for a different module all become named errors rather than a silent skip.
  • Keep the existing preview modal — it is the right interaction; feed it the server's validation result instead of the client's guess.

03

Student status changes with a reason and a document

New table + upload Medium
“Kuri Edit ya Student hagomba kujyaho uburyo bwo guhindura Active, innactive, graduand, granduate, Rejected with reason, Drop out with reason, Death with Upload supporting document.”
What it asks for

The Edit Student screen must offer the full set of states — Active, Inactive, Graduand, Graduate, Rejected, Dropped out, Deceased — and must capture why: a reason for Rejected and Dropped out, and a supporting document for a death.

Where the code stands

Commit c7f7e0d already added Graduand, Rejected and Dropped out to the picker in StudentDetailsPage.tsx and folded the legacy spellings through normaliseStudentState(). Three things are still missing: Deceased is not an option, no reason is captured for any state, and there is no upload. The column itself, student.student_state VARCHAR(40), is free text with no history — changing a status today overwrites the previous value with no trace of who did it or why.

What to build
  • Migration 144: student_status_changes — student id, previous state, new state, reason, optional document_id, actor and timestamp. This is the audit trail the current column cannot provide, and item 01 writes into it too.
  • Add Deceased to STUDENT_STATES and make the state list a shared constant, so the students list filter, the export and this picker cannot drift apart again.
  • Server-side rules in StudentController::update(): reason required for Rejected and Dropped out, document required for Deceased. Reject the write rather than silently storing a bare state.
  • A modal on the status field that asks for the reason and, for a death, takes the file through the existing student-document upload path — no new storage mechanism.
  • Show the change history on the student record, and log through SystemLogService as the other state changes already do.

04

Date-range filters on applications and every report

Backend + UI Medium — wide surface
“Kuri Applications, n'ahandi hakenerwa report hajyeho filter by Date range (From … to …).”
What it asks for

A From … To … filter on the applications list — and on the other screens that produce reports.

Where the code stands

ApplicationAdminController::index() accepts eleven filters — search, status, department, intake, campus, mode of study, academic year, level, gender, payment status, sort — and not one of them is a date. The same is true of export(), statistics() and getDashboardStats(), so a registrar cannot answer “how many applications came in last month”.

What to build
  • Accept submitted_from and submitted_to in index(), export(), statistics() and getDashboardStats(), passed through paginateFiltered() to an indexed range on submitted_at. Both bounds inclusive; either one alone is valid.
  • One shared DateRangeFilter component with presets — this month, last month, this academic year, custom — so every report gets the same control rather than four hand-rolled pairs of date inputs.
  • Roll it out to the other report screens in the same pass: billing summary and export, student export, service-request reports, academic analytics.
  • Carry the active range into every export so the downloaded file matches what is on screen.

07

Students edit their own full profile

Policy + endpoint Needs a decision
“Student Portal ahabwe uburenganzira bwo guhindura full inforamtion ze (imyirondoro ye yose).”
What it asks for

A student should be able to edit their whole personal record from the portal, not a fragment of it.

Where the code stands

StudentController::updateMe() whitelists seven columns: phone, marital status, and the five residency fields. Everything else in the payload is dropped on purpose — the comment says so explicitly, to stop a student rewriting their own programme or level.

Decide before building

“Full information” cannot mean every column. regnumber, faculty, department, std_option, current_level, student_state and sponsor are the institution's record of the student and must stay locked — a student who can edit them can move themselves into another programme. The registry needs to confirm the split below.

Proposed three-tier split
  • Free to edit — phone, email, marital status, spouse, disability, and the five residency fields. Saves immediately, as today.
  • Edit with evidence — names, date of birth, gender, nationality, national ID, parents' names. These are identity fields on certificates and transcripts, so they go through a change request with a supporting document, approved by the registry. The service-request stage-chain the system already uses is the natural home for this rather than a second approval mechanism.
  • Locked — registration number, faculty, department, programme, level, status, sponsor. Registry-only, unchanged.

ID card: QR, print and download

Buttons + verification Small
“Ku ikarita y'ishuri harayaho qrcode kandi habeho print na Download.”
What it asks for

The student ID card needs a QR code, and the screen needs both a print and a download action.

Where the code stands

The QR code is already on the card. StudentIdCardHelper renders it with chillerlan/php-qrcode, pointing at the public verification page for that card's barcode. StudentIdController::card() streams a single card as PDF and batchPrint() streams up to 200. What the workspace lacks is the per-student controls: StudentIdCardsPage.tsx offers only “Print selected” for a multi-row selection.

What to build
  • Per-row Download PDF and Print actions on the ID-card workspace, and the same pair inside the card preview modal — print opens the PDF and calls the browser print dialog; download saves it.
  • Confirm the QR renders on the production host. The helper falls back from the GD PNG path to inline SVG; verify which branch runs there and that a phone actually resolves the encoded URL to a working verification page.
  • Expose the same download on the student's own portal if the registry wants students printing their own replacement cards — worth asking, as it changes who the audience is.

09

Lecturers see their class by intake and programme type

Data model + filters Large Needs a decision
“Mwalimu muri acount ye agomba kubona abanyeshuri hakurikkijwe Inatake, Class, program (weekend, day cg holidays) kandi system yose igomba kukugira inatake 3 gusa (January, May na September)… mwarimu abona abanyeshuri bavanze muri inatake nyinshi.”
What it asks for

A lecturer's class list must show, and filter by, intake, class and programme type (weekend / day / holiday). The whole system should recognise exactly three intakes — January, May, September. The reason given is concrete: a lecturer's class mixes students from several intakes and there is currently no way to tell them apart.

Where the code stands

TeacherController::students() returns registration number, name, gender, contact, level and module codes — no intake, no programme type, no filters at all. The data underneath is the harder problem: student.intake is VARCHAR(40) free text, the intakes table is open-ended with no seeded values, and mode_of_study (Day / Weekend) exists on the application record but never lands on the student row.

What to build
  • Audit the distinct values in student.intake first. Everything else depends on how far the real data is from the three intended intakes — do this before writing the migration, not after.
  • Migration 146: seed January / May / September in intakes, add student.intake_id as a proper foreign key, backfill from the free-text column, and add student.mode_of_study backfilled from the linked application. Keep the legacy text column beside the id rather than replacing it, per the project's convention for id-plus-name columns.
  • Anything that will not map cleanly gets reported for the registry to resolve by hand — never guessed.
  • Add intake_id, mode_of_study and level to the lecturer's students query and course enrollment list, and filter controls in the teacher portal, with each student's intake visible on the row so a mixed class reads at a glance.
Decide before building

Two questions. “Class” — does it mean the academic level, the programme cohort, or the timetabled group? The system has no “class” entity, so this determines whether the filter is a rename of an existing field or a new one. And do the three intakes replace what is in the table, or sit alongside historical intakes that must stay readable for past cohorts?

10

Billing by programme, with arrears paid first

Filter + columns + rule Large
“Muri finace Billing igomba kuzana abanyeshuri bose bo muri faculity runaka, department, option kandi hakabaho table iriho Billing, openbalance, na Total, niba umunyeshuri yishyuye ibanze yishyure ikirarane.”
What it asks for

Billing must list every student in a chosen faculty, department and option (programme), in a table showing Billing, Open balance and Total. And a payment must clear arrears before anything else.

Where the code stands

FeeController::listAllStudentsWithStatus() already returns every student including those with no invoices, filtered by academic year, semester, faculty and department — but not by option, which is the level the registry works at. On arrears: FeeService does create an ARREARS invoice rolling forward last year's balance, but recordPayment() takes a single invoice_id and posts against it with no ordering rule. Nothing stops a student paying this year's tuition while an arrears invoice sits open — which is precisely what the report is asking to prevent.

What to build
  • Add option_id to the billing filters, on both the summary and all-students endpoints and their export, and to the filter panel on StudentBillingPage.tsx.
  • Settle the three column definitions with finance before implementing — see the note below — then render them as a table with tabular-nums alignment and a totals row.
  • Enforce oldest-debt-first in recordPayment(). Recommended: keep invoice_id as the target but refuse the write when an older unpaid invoice exists, with an error naming that invoice — an explicit refusal a finance officer can act on beats a silent re-allocation of their money.
  • Offer a “Pay oldest first” action that allocates one amount across invoices in date order, so the officer has a correct path and not just a blocked one.
  • Apply the same rule to the online payment path, or arrears can be bypassed by paying through the gateway.
Decide before building

Finance must define the three columns exactly. Read most naturally: Billing = invoiced this year, Open balance = brought forward from previous years, Total = what the student owes now. Getting this wrong produces a table that looks right and reconciles to nothing.

Two things are worth raising with the registry directly.
